This is a source-tree inventory, not a production deployment export. It reflects
the four working trees inspected on 2026-10-14. The import graph is generated
separately by `scripts/architecture-import-graph.py` and includes the nested Go
SDK module. Working-tree status counts and validation commands are recorded in
`implementation-status.md`; no file contents or secrets are captured there.

## Build and test prerequisites observed

- Engine, its nested Go SDK, and Cloud declare Go `1.25.0`; the current local
  toolchain is Go `1.25.0`.
- Engine's embedded SPA uses a `go:embed` pattern over `workspace/dist`. A bare
  Go test/list/build can fail when that directory is absent; `make build`
  produces the embedded UI, while CI currently creates a placeholder before Go
  tests and builds.
- The embedded UI and standalone workspace UI are Bun projects. The TypeScript
  SDK's tests and contract check also use Bun. The inspected machine has Bun
  `1.3.6`; CI currently requests `bun-version: latest`, and the Docker UI stage
  uses the floating `oven/bun:1-alpine` tag.
- Self-host Engine Compose pins MySQL `8.4.11`, but Engine CI starts MySQL `8.0`.
  Cloud Compose uses MySQL `8.4`; Cloud's disposable-stack instructions also
  include MySQL `8.0`. This is the observed validation matrix, not evidence that
  every version is equally supported.
- The previously failing initial Engine package enumeration was specifically
  caused by missing embedded SPA assets (`workspace/spa.go: pattern all:dist:
  no matching files found`). After the supported `make build`, strict ordinary
  `go list -json ./...` succeeded. No `go list -e` output was used for the
  committed graph.

## Public and consumer contracts

- Engine route registration is composed in `cli/serve.go`. The registered
  public route families and owners are:

  | Prefix/family | Registration owner | Notes |
  |---|---|---|
  | `/api/auth/*` | `auth/session.go` | Login/logout, provider discovery, magic links, current session. |
  | `/api/v1/*` | `api/router.go` and route modules | Canonical authenticated API, including resources, kernel, system, AI, analytics, scripts, extensions and conversations. |
  | `/api/*` | `api/router.go` and route modules | Legacy compatibility surface; same handler families as canonical API. |
  | `/api/v2/requests*` | `api/requests_api.go` | Typed direct-task requests, response, reassignment, cancellation, history and read receipt. |
  | `/api/v1/public/*`, `/api/public/*` | `api/router.go` | Public resource/view/file delivery and the M-Pesa provider callback. |
  | `/api/console/*` | `api/console.go`, mounted in `cli/serve.go` | Console sign-in, onboarding and tenant administration routes. |
  | `/api/management/v2/*` | `api/management_inspect.go`, conditionally mounted in `cli/serve.go` | Bearer-authenticated Engine management inspection routes. |
  | `/health`, `/readyz`, `/_kora/admin/reload-site` | `cli/serve.go` | Health/readiness and operator reload endpoints. |
  | `/workspace/*` | `workspace/handler.go` or `workspace/spa.go` | Server-rendered or SPA workspace distribution, selected at startup. |

  `route-inventory.json` is generated by invoking the same Gin registration
  functions and contains 273 registered method/path/handler entries, plus 17
  CLI-conditional routes and two mutually exclusive workspace fallback modes.
  `go run ./cmd/routeinventory -check` detects drift. The inventory explicitly
  separates routes registered by shared API functions from direct CLI routes;
  tenant-host routing and DocType-specific behavior remain data-dependent.
  OpenAPI output is assembled in `api/openapi.go`; it covers the handler's
  DocType schema surface and is not a complete registry of every Gin route.
- Engine fixed wire contracts are in `contract/`; generated, versioned
  artifacts are `contract/schema/engine-v1.json`, `engine-v2.json` and their
  TypeScript validators in `contract/generated/`. Dynamic DocType OpenAPI
  remains a separate handwritten generator.
- Cloud consumes Go contracts from the Engine module and keeps management and
  Cloud-domain DTOs in `cloud/` and `internal/domain/`.
- Standalone UI's hand-authored API types are in `src/types/api.ts`; it also
  vendors the generated Engine v2 validators in `src/generated/engine-v2.ts`.
  The embedded UI has the same generated bundle under `ui/src/generated/`.
  SDK types and validators are in `src/types.ts` and `src/validation.ts`; its
  generated Engine v2 bundle is `src/generated/engine-v2.ts`. All three copies
  currently match the Engine artifact digest, and each consumer's contract
  check validates its own manifest/bytes.
- Shared organizational-runtime JSON fixture copies currently exist in Engine,
  Cloud and standalone UI. Engine additionally has a site-directory v1 fixture.
  Their paths and SHA-256 values are listed in
  `contract-fixture-manifest.json`. Existing repository tests decode or compare
  these fixtures. The manifest also checks embedded UI, Studio UI and SDK
  generated Engine v2 copies against Engine. It does not imply a released/pinned
  package version.

## Persisted workflow and durable-work formats

- Unified Engine v2 workflow definitions, instances, attempts, timers, signals,
  receipts, previews, and history use the versioned stores under
  `_kora_workflow_definition` and `_kora_workflow_*` execution tables.
- The former document lifecycle configuration and actor/timer runtime are
  retired. Engine does not load, migrate, execute, or recover those formats.
- Analytics retry state is JSONL in the analytics WAL. Transactional event
  publication uses `_kora_outbox`; source ordering uses
  `_kora_event_sequence` and `_kora_outbox.source_sequence`.
- Request and workflow v2 persistence is represented in current source and
  tests, but no production rows or pending-instance population was queried.

## Current runtime ownership map

- `cli/serve.go` owns process assembly and the engine shutdown sequence.
- The tenant runtime manager owns loaded tenant generations and their attached
  resources; `api/router.go` resolves request context to a pinned generation.
- Tenant runtime services own analytics, event/outbox, realtime, webhook,
  script-store, secret-store and attachment-storage dependencies. Pool-level
  endpoint admission is owned by `internal/dbaccess`; its configured per-process
  limits and replica allocation assumptions are documented in
  `resource-budgets.md`.
- Cloud is a separate process/repository. Its direct Engine implementation
  imports listed below are current coupling, not an ownership transfer.

## Deployment assignment evidence

Cloud source contracts contain `deployment_id`; Engine and Cloud source/tests
also retain legacy `runtime_cell_id` compatibility references. Checked-in test
fixtures use synthetic IDs only. No authoritative production assignment export,
live consumer telemetry, or production credentials were present in the
inspected repositories, and no production system was queried. Consequently the
actual nondefault assignment inventory required before G9 cutover remains an
external G0 gate.

The Engine checkout contains ignored local `sites/` data, but no tracked
site/deployment assignment files. Those tenant-specific files were not opened
or used as a substitute for an authoritative production assignment export.
Cloud's tracked assignment-like examples are typed contracts and synthetic
unit fixtures, not a live tenant-to-deployment inventory.

## Cloud-to-Engine implementation imports

At the G0 inventory snapshot, the Cloud production import graph had these
direct Engine edges:

| Cloud package | Engine packages |
|---|---|
| `cloud` | `contract`, `site` |
| `cmd/site-directory-migrate` | `db`, `site` |
| `internal/app` | `contract`, `site` |
| `internal/contentcatalog`, `internal/domain` | `contract` |
| `internal/messaging` | `doctype` |
| `internal/platform` | `contract`, `db`, `doctype`, `natsprovider`, `script`, `sdk/management`, `site` |
| `internal/provisioning` | `contract`, `site` |

These snapshot edges are selected from `import-graph.json` by `from_module=cloud` and
`kind=production`; internal and external test imports are separately tagged.
The `contract` and `sdk/management` edges are intended typed seams. The other
Engine implementation imports are current G7/G10 coupling, not assumed
supported boundaries.

On 2026-10-16 the normal Cloud build moved the remaining `db`, `doctype`, and
`site` imports into `internal/platform/legacy_engine_compat.go`, which is
included only by the `kora_legacy_engine` build tag. The generated default
import graph must therefore show no Cloud production imports of Engine
implementation packages. The tagged adapter remains a temporary compatibility
artifact and is exercised separately; it is not part of the normal Cloud
image.

## Database support evidence

The current support claims and limitations are maintained in
`database-support-matrix.md`. MySQL is the default/self-host path; PostgreSQL and
remote LibSQL have dialect implementations and partial real-database test
coverage. No complete all-package version matrix or pooler compatibility run is
claimed. Test DSNs are opt-in and must be disposable before running integration
tests.
