# Kernel mutation migration: test and Go standards

REST endpoints remain compatibility adapters for the MVP. They translate HTTP into canonical kernel commands and translate results back to the existing response/status contract; they do not own business mutation logic.

## Required tests before each cutover

Treat this sequence as test-first: write and run the contract tests against the current behavior, record any intentional contract change with approval, then implement the kernel adapter. A test marked as a cutover gate must exist and pass before that writer is changed; do not write the migration first and retrofit tests afterward. Do not delete the old writer until the new-path tests pass against each supported database dialect.

For work already migrated before this gate was adopted, add the characterization tests now and label them as *post-cutover regression coverage*; do not claim they were run against the removed writer. For every remaining writer, land the tests in a test-only change first (or make the test commit precede the implementation commit in the same review), run them on the current path, and attach the observed contract. The migration change must then run those same assertions unchanged. This keeps historical evidence honest while making all remaining cutovers genuinely test-first.

### Minimum test-first deliverable

Before changing a writer, its PR must include the tests below (or point to an existing test that proves the same behavior). The test must be run once against the current path to establish the contract, then run unchanged against the kernel path. A test that only proves `Execute` returns success is not sufficient.

1. **Boundary contract tests**: characterize route/method, auth context, request fields, success status and JSON envelope, error status/code, and any headers consumed by the MVP UI/provider. For UI-backed routes, test the real API client wrapper as well as the HTTP handler.
2. **Mutation invariant tests**: assert the exact persisted parent/child state and actor/site ownership; assert one authorization decision, lifecycle sequence, audit row, outbox event, and receipt where applicable. Assert that denied/invalid commands leave all of those unchanged.
3. **Failure and retry tests**: inject a database or provider failure at each write boundary and assert full rollback; replay the same idempotency key and payload, then reuse the key with a changed payload; assert stable results and no duplicate side effects.
4. **Race tests**: coordinate duplicate-key and expected-version contenders with channels/barriers (not sleeps); assert one durable mutation and deterministic replay/conflict outcomes under `go test -race`.
5. **Portability tests**: run each SQL/transaction cutover test on every supported dialect. Do not treat compilation, mocks, or a skipped live-database test as portability evidence.
6. **Resource/performance tests**: add deterministic correctness/resource-bound checks to CI and a repeatable database load/benchmark command for latency distributions, throughput, allocations, SQL count, pool waits, and transaction time. Never put host-specific timing assertions in unit tests.

The first implementation slice should make the current REST contract test fail only on the intended missing kernel guarantees (for example, absent audit/outbox/idempotency), not on response shape or status. Keep that test in the final change. If an existing route has no characterized contract, stop at the test and record the observed behavior before implementing it; do not invent a replacement contract while migrating.

| Area | Acceptance tests |
|---|---|
| REST contract | MySQL integration create/update/delete; status, `{data, meta}` shape, full document, delete message, and 400/403/404/409 mappings |
| Atomicity | Commit and forced-failure tests for row + receipt + audit + outbox; assert rollback leaves none of them |
| Validation/hooks | Required/default/unknown/read-only fields, child tables, linked records, validate/before/after hooks; assert hooks run once and after-hooks only follow commit |
| Authorization | Human/service/agent/public grants, create/write/delete denial, tenant isolation; no adapter may widen a kernel grant |
| Retry/concurrency | Same key/payload replay returns the original result without repeating effects; changed payload conflicts; expected-version success/stale conflict; concurrent duplicate key |
| Workflow/UI actions | Every MVP-used workflow, manifest create/update/transition action, and error/notification behavior |
| Frontend callers | Exercise the MVP resource and workflow clients against their existing routes and assert consumed response shapes/statuses |
| Other writers | Audit AI, script, payment, public-form, and view-action writes; add command-specific tests before migrating each. Keep platform stores and multi-record domain invariants explicit, not generic CRUD shortcuts. |

### Required test-first review artifact

Before implementation begins for a remaining writer, attach a short test matrix to its PR with one row per externally observable behavior: current request/event input, actor/site, expected response, persisted state, side effects, and failure outcome. At minimum include:

| Test dimension | Required evidence before changing production code |
|---|---|
| Compatibility | Existing method/path or provider event, auth context, status/body/headers, and frontend-consumed fields captured from a live handler/client test |
| Success invariants | Exact record and child state, owner/site, lifecycle order/count, audit/outbox/receipt counts, and response projection |
| Rejection | Invalid input, denied actor, missing/foreign record, stale version, duplicate/changed idempotency key; assert no durable partial effects |
| Failure boundary | Inject failure before and after the first durable write and at each secondary write/provider boundary; assert rollback or explicitly documented recovery semantics |
| Replay/race | Same-key replay plus changed payload; barrier-coordinated concurrent duplicates and expected-version updates; assert deterministic winner/result |
| Portability | Same transaction contract on each supported live database; list configured dialects and explicit skips, never count a skip as a pass |
| Cost | Repeatable benchmark/load fixture and baseline captured before the writer changes; report latency distribution, throughput, allocations, SQL/transaction counts and pool wait |

The reviewer blocks cutover if any row lacks either a passing test or a written, approved reason it does not apply. “Covered by unit tests” is not enough for HTTP serialization, SQL transactions, database constraints, or driver behavior. After implementation, attach the test command/output and verify the original contract assertions were not weakened.

### Test-first order and evidence

For every writer slice, use this order and keep the evidence with the change:

1. Add a characterization test for the current externally observable contract: HTTP or provider result, status/error mapping, persisted fields, and side effects. Do not characterize accidental SQL call order.
2. Add the desired kernel invariants as assertions: one authorization decision, one transaction boundary, exactly-once hooks, receipt/audit/outbox behavior, and rollback behavior. These assertions should fail against the old writer when the old path lacks the guarantee.
3. Run the test on the current writer and record which assertions expose a known parity gap. If any intentional contract change is proposed, capture it explicitly before implementation; don't silently weaken the test.
4. Implement the adapter and rerun the same test without changing its contract assertions. Add unit tests only for pure mapping/policy behavior; use isolated database integration tests for SQL, transaction, and dialect behavior.
5. Remove the old writer only when all relevant cutover tests pass and `rg`/call-graph review shows no remaining business-record caller. Keep platform configuration, secret, script-definition, and analytics stores out of this cutover unless separately scoped.

### Pull-request cutover checklist

For each migrated write surface, the change should be reviewable in this order:

1. Add the contract and failure tests first, run them against the existing writer, and record which kernel guarantees currently fail. Keep the new tests in the final patch; do not replace them with weaker tests after the implementation changes.
2. Implement the smallest adapter that builds a typed kernel command. Keep provider/webhook parsing and HTTP response mapping at the boundary; keep authorization, document validation, transaction ownership, idempotency, audit, and outbox semantics in the kernel.
3. Run focused unit tests, isolated live-database tests, frontend contract tests where the UI calls the surface, and race tests for concurrent/idempotent paths. A skipped tagged test is a visible outstanding gate, not a pass.
4. Compare before/after performance using the same fixture and environment. Attach benchmark output and load-test percentiles; explain any regression over the guardrail before merging.
5. Search runtime call sites and dynamic-table SQL for remaining direct DocType writes, then remove the obsolete writer and its tests/helpers in the same slice. Do not remove shared ORM transaction primitives that the kernel itself still needs.

The PR description should identify the user-visible contract preserved, kernel guarantees added, tests run (including dialect and skip status), direct-writer search result, and measured performance delta. If one of these is unavailable, state the exact remaining gate instead of describing the slice as complete.

For rollback/failure cases, assert the full state tuple, not only the HTTP response: business rows, operation audit, idempotency receipt, and outbox event. For concurrency cases, use barriers/channels rather than sleeps. For retries, assert both the returned original result and exactly-once side effects.

## Go patterns

- One transaction owner: the kernel owns begin/commit/rollback for a mutation plus receipt, audit, and outbox; ORM `*InTx` methods never commit or open nested transactions.
- Keep authorization, validation, optimistic concurrency, and idempotency in the command pipeline. HTTP adapters parse, resolve identity/context, map stable errors, and preserve response contracts.
- Thread request contexts to database and external calls; enforce an operation deadline. Do not detach synchronous work into goroutines.
- Wrap typed internal errors; map them to stable client codes. Never return SQL, credentials, or raw driver errors to clients.
- Keep DB work bounded: select only needed fields, avoid N+1 reads, batch child writes in the transaction, preserve tenant predicates, and index receipt lookup by `(site, idempotency_key)`.
- Never hold a transaction across network/model calls or slow scripts. Post-commit work is explicitly best-effort or delivered through the outbox.
- Prefer small typed payload/result structs and explicit command dispatch. Avoid permission logic duplicated in adapters/ORM and branches that silently choose a legacy path.
- Keep package boundaries directional: HTTP/API adapts contracts to kernel commands; kernel coordinates policy and transaction boundaries; ORM executes SQL; domain packages own rules. Do not make the kernel depend on API or UI packages.
- Use injected interfaces for external effects (provider calls, clock, script runner) so tests can prove timeout, retry, and failure behavior without live services. Keep interfaces narrow and defined by the consumer.
- Pass immutable command input by value; clone/normalize mutable document data at the boundary. Avoid shared mutable maps across goroutines and avoid global mutable test/runtime state.
- Make side effects explicit in command definitions (permission operation, touched records, event types, idempotency policy). Use typed errors with `errors.Is`/`errors.As`; do not branch on error strings.
- Do not ignore durability errors. Best-effort behavior must be named, logged with identifiers (not secrets/payload dumps), and tested as such. Never silently swallow failed payment, audit, or outbox writes.
- Use table-driven tests for pure validation/mapping rules, but keep integration tests scenario-named and readable. Tests must use isolated tenant/schema/database state and `t.Cleanup`; no order dependence or live customer/site mutations.
- Run `go test -race` on concurrency-sensitive kernel, ORM, and API packages. Add fuzz tests for untrusted JSON/filter/command decoding when parsers have non-trivial branching; seed them with valid and malformed examples.
- Use `errors.Is`/`errors.As`; check errors that affect durability. Run `gofmt`, targeted tests, `go test ./...`, `go vet ./...`, and race tests on kernel/ORM/API where practical.
- Keep exported APIs small and documented; keep types and helpers close to the package that owns their invariants. Prefer one obvious command path and explicit types over fallback/legacy branches. Avoid introducing a generic framework for the sake of one adapter.
- Treat transaction and request lifetimes explicitly: never retain `*sql.Tx`, request context, or mutable document maps after their owner returns. Do not capture loop variables in goroutines; do not add goroutines to synchronous mutation paths.
- Keep tests deterministic: inject clocks, provider/script effects, and barriers where needed. Avoid global mutable registries and test order dependencies. For integration tests, create isolated schemas/databases and clean them with `t.Cleanup`.
- Run `go test -race` for replay/concurrency and hook recursion tests; run fuzzing for operation decoding and reference resolution with bounded inputs so fuzz cases cannot create unbounded work.

## Performance gate

Capture a baseline before each cutover and compare on the same Go/MySQL versions, schema/data, pool settings, and load. Measure create/update/delete at concurrency 1 and representative concurrency: p50/p95/p99 latency, throughput, errors, allocations/op, SQL statements/op, pool wait, and transaction time. Split spans across validation, hooks, SQL, outbox, and response.

Use `go test -bench . -benchmem` for microbenchmarks and a fixed integration/load harness for end-to-end measurements. Compare repeated runs; do not put wall-clock thresholds in unit tests. Initial guardrail: avoid more than 10% p95 or throughput regression at equal load unless measured consistency/audit benefits justify and record it. Tighten the budget only after a stable baseline. Optimize from profiles (`pprof`) and query plans, not assumptions.

### Query-plan spot check

On 2026-10-02, read-only MySQL `EXPLAIN` inspection against `kora-mvp-demo-20260930` confirmed that the idempotency lookup's `(site, idempotency_key)` primary key and the audit lookup's `idx_audit_operation` are available. The live site had zero receipt/audit rows and only two outbox rows, so its outbox plan is not a useful scale signal. In a session-local 10,000-row outbox fixture with an even mix and nearly all pending events due (no persistent site data changed), the publisher's combined pending/expired-lease predicate scanned and filesorted the table; candidate indexes did not change that cost-based choice. A second temporary fixture with a more selective mix (5% due pending, 5% future pending, 1% expired leases, 89% published) and only production indexes selected `idx_outbox_pending` for the combined poll and estimated 600 candidate rows with filesort; the due-pending branch estimated 500 rows via a range scan, the expired branch estimated 100 rows using the status prefix, and the dispatcher estimated/sorted 1,000 pending rows. The plan is therefore sensitive to event-state proportions; current evidence does not justify adding write-amplifying indexes or splitting the portable poll query. Revisit with production backlog proportions and measure worker throughput, poll latency, and write cost on supported dialects. This is not evidence that receipt or audit lookups need more indexes.

### Go performance standards

- Benchmark the hot operation itself with `-benchmem`; use `b.ReportAllocs()` and representative payload sizes. Establish a baseline before optimization and compare on the same Go version, hardware, database, and data fixture.
- Keep benchmarks representative and interpretable: separate setup from timed work, reset counters after fixtures, avoid logging in the measured loop, use `b.ResetTimer`, and report custom metrics (`b.ReportMetric`) for SQL/op or bytes/op where useful. Run multiple samples (`-count`) and compare distributions with `benchstat`; a single short run is instrumentation evidence, not a performance claim.
- Keep request-path allocations proportional to payload size. Avoid repeated JSON marshal/unmarshal, reflection, per-record schema lookups, and copying large documents in loops; cache immutable registry metadata at site/runtime construction, not in unsynchronized package globals. Keep callbacks and policy context operation-scoped; never swap tenant/request-specific functions through package globals.
- Bound concurrency and resource use: request/script timeouts, DB pool limits, capped list sizes, bounded HTTP response bodies, and no unbounded goroutine fan-out. Never spawn fire-and-forget goroutines for mutation durability.
- Minimize round trips: batch child rows and related writes within one transaction, avoid N+1 lookups, and use indexed lookups for idempotency/provider references. Confirm important queries with `EXPLAIN` on production-shaped fixtures.
- Keep transaction duration short. Do validation that does not depend on locked state before begin where safe; inside the transaction re-check invariants and perform only bounded DB work. Provider/model/script network calls stay outside transactions.
- Profile CPU, heap, mutex/blocking, and database wait separately (`pprof`/tracing). Do not accept speculative pooling, caching, or custom SQL that makes correctness harder without a repeatable measured win.
- On a demonstrated hot path, capture CPU and allocation profiles before changing code; name the dominant cost, make one bounded change, then rerun the same profile/benchmark. Do not optimize based only on source inspection or one end-to-end latency number.
- Keep benchmark names and fixtures stable (`BenchmarkKernelRecordCreate`, `BenchmarkKernelRecordUpdate`, `BenchmarkPOSMutationBundle`, `BenchmarkScriptProviderCRUD`); report allocations and use the same representative DocType/child-table sizes before and after. Store raw output or a concise comparison in the change record so a claimed improvement is reproducible.
- Performance tests should assert resource bounds and correctness, not fragile machine-specific nanosecond cutoffs. The test-only SQL measurement driver currently covers the REST CRUD load test and POS bundle/CRUD benchmarks; extend the same harness to other write surfaces when adding or changing them. For CI, use a broad regression alert only on a controlled runner; use local/database load measurements for p95/p99 decisions.
- Scale the MySQL CRUD integration load fixture with `KORA_PERF_WORKERS`, `KORA_PERF_RECORDS_PER_WORKER`, and optional `KORA_PERF_MAX_OPEN_CONNS`; defaults remain 8 workers × 12 records with the normal `database/sql` pool. Set `KORA_PERF_DISABLE_SQL_INSTRUMENTATION=1` for raw latency comparisons when the legacy reference does not use the test SQL-counting driver; those runs omit SQL/transaction metrics. Invalid values and fixture sizes above 10,000 records fail fast. Record the selected worker count and pool cap with every result; do not compare runs with different pool settings as though they were identical.
- Treat unexpected complexity as a performance cost: every cache, pool, goroutine, reflection layer, or abstraction needs a measured bottleneck and a test for its invalidation/lifetime/resource bound. Prefer removing round trips or repeated work over adding concurrency; concurrency is not a substitute for bounded work.
- Establish the actual starting numbers before setting tighter budgets. The 10% p95/throughput guardrail is a review threshold, not permission to trade away atomicity, authorization, or data durability.
